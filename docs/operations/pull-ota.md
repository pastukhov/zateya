# Pull OTA: подготовка релиза

Затея пока **не обновляется сама на реальном устройстве**: OTA-клиент собран,
но разметка с двумя OTA-слотами ещё не установлена по USB. Этот этап готовит
контейнер сборки, подписанный образ, закрытые эндпоинты backend и pull-клиент.
Не публикуйте `stable.json`
для повседневного устройства до аппаратной проверки.

Кандидатная таблица `firmware/partitions.ota.csv` рассчитана на 8 МиБ:
`otadata` и два слота по 3 МиБ. Текущая `partitions.csv` не меняется.
Для первого перехода понадобятся проверка фактической flash по USB,
резервная копия NVS и установка новой таблицы вместе с OTA-совместимой
прошивкой. Само обновление приложения позднее не должно менять таблицу
разделов или bootloader.

Секрет подписи хранится только в `./data/firmware-signing/ota-p256.pem`.
Он не монтируется в backend. Публичный ключ `ota-p256-public.pem` из этой
же пары встраивается в собранный образ. Потеря
закрытого ключа лишит возможности выпускать обновления для уже прошитого
устройства; храните его резервную копию вне сервера. Ключ устройства,
токены, адрес сервера и Wi-Fi не должны попадать в OTA-образ.

Подготовка каталогов и ключа от корня репозитория:

```sh
./deploy/prepare-data.sh
openssl ecparam -name prime256v1 -genkey -noout -out data/firmware-signing/ota-p256.pem
openssl pkey -in data/firmware-signing/ota-p256.pem -pubout \
  -out data/firmware-signing/ota-p256-public.pem
chmod 600 data/firmware-signing/ota-p256.pem
./deploy/prepare-data.sh
```

Создавайте пару только один раз. `prepare-data.sh` не заменяет существующий
ключ и назначает каталоги контейнерному UID/GID. Не помещайте
закрытый ключ в Git и не передавайте его в переменных окружения Compose.

Сборка кандидата с монотонным номером выпуска:

```sh
docker compose --profile firmware build firmware-builder
docker compose --profile firmware run --rm \
  -e GIT_REVISION="$(git rev-parse HEAD)" firmware-builder build 1
```

Образ, манифест, подпись, bootloader, таблица разделов и начальный `otadata`
появляются в `data/firmware/releases/1/`.
Сборка сама **не** меняет `data/firmware/stable.json`. Повторный номер
отклоняется. После проверки релиза публикация выполняется отдельно:

```sh
docker compose --profile firmware run --rm firmware-builder publish 1
```

Публикация проверяет подпись, SHA-256 и размер, затем атомарно обновляет
указатель `stable.json`. Более старый номер или тот же номер с иным
образом отклоняются. Если не хотите раздавать образ, удалите указатель
`stable.json`, оставив кандидаты для анализа.

Backend читает `./data/firmware` только для чтения и обслуживает
`GET /api/firmware/manifest?board=sticks3&layout=ota-v1&current_seq=N`
и `GET /api/firmware/images/<sha256>.bin`. Оба запроса требуют
`X-Device-Id` и `Authorization: Bearer <токен устройства>`; без более
новой совместимой версии первый отвечает 204. Манифест подписан ECDSA
P-256, а образ отдаётся только по хешу явно опубликованного релиза.
Прокси Алисы эти пути не пропускает.

Клиент проверяет наличие обновления один раз после готовности сети и ответа
backend 200 при каждом запуске/пробуждении. Если в этот момент идёт запись
или нет USB-питания, он до десяти минут ждёт безопасных условий; затем
повторит проверку при новом запуске. Он принимает только более новый
номер для `sticks3`/`ota-v1`, проверяет подпись встроенным публичным ключом,
размер, SHA-256 и записывает только неактивный слот. Проверка и установка
не должны мешать записи; на время установки запрещены запись и сон, экран
показывает прогресс. Сервер может быть недоступен — обычная работа от этого
не блокируется. Скачивание ограничено десятью минутами; после ошибки
следующая попытка начинается при новом запуске. Новый образ подтверждается
локальной проверкой LCD, памяти, инициализации аудио, получения данных I2S и
нескольких проходов основного цикла; при неуспехе он должен откатиться.
Эта проверка не измеряет качество записанного звука. Отклонённый номер
не устанавливается повторно.

Пока на плате не проверено измерение процента заряда, обновление разрешено
**только при USB-питании**. Это строже исходного плана «USB или батарея от
50%»: неизвестный заряд никогда не принимается за достаточный.

Ограничения текущего этапа: контейнерная сборка и тесты не подтверждают
размер реальной flash, работу проверки подписи на плате, запись OTA-слота,
откат и поведение при потере
питания. Эти проверки остаются в [плане](../superpowers/plans/2026-10-03-recorder-pull-ota.md).
