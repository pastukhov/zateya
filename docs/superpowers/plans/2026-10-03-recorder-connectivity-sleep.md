## Общие ограничения

- Рабочий репозиторий `/home/artem/repos/zateya`; перед изменениями проверить ветку, status и подтянуть изменения без потери чужих правок.
- Стадия прототипа: не создавать слой миграций и совместимости старых протоколов.
- Не выдавать ключи, токены и сохранённые адреса в setup, логи или метрики.
- Все новые пользовательские сообщения по-русски; Затея — женского рода.
- Каждый программный этап: воспроизводящий тест → ожидаемое падение → реализация → зелёные проверки → отдельный commit и push по AGENTS.md.
- Host-тесты и успешная сборка не доказывают работу реального устройства. Аппаратные пункты оставлять открытыми до проверки.
- Команды firmware запускать из `firmware/`: `pio test -e native`, `pio run -e sticks3`. Сначала проверить доступный PlatformIO и Python, не переиспользовать сломанное окружение после обновления Python.

**Goal:** Разделить ожидание Wi-Fi, времени, VPN и backend и не прерывать подключение преждевременным сном.

**Architecture:** Host-тестируемая политика времени/состояний; ESP-адаптер выполняет сетевые операции. Монотонные дедлайны независимо от SNTP, без вечного busy.

**Tech Stack:** C, ESP-IDF 5.5.3, PlatformIO, Python/FastAPI, Docker Compose.

## Этап 1 — сейчас: сон при подключении

- [ ] Зафиксировать предлагаемые значения политики: один общий бюджет подключения 120 секунд после boot/wake; после истечения обычный idle timer (по умолчанию 30 секунд). Flap сети не продлевает бюджет бесконечно.
- [ ] Native-тесты: нет сна на 30-й секунде при подключении; на 120-й снимается hold; после idle timeout разрешён сон; успех раньше дедлайна снимает hold; выключенный VPN не задерживает; monotonic wrap работает.
- [ ] Включить `sleep_hold` в текущий `busy` power policy без изменения сохранённой пользовательской яркости/таймера; не менять смысл реально выполняющейся записи/воспроизведения.
- [ ] Не вводить новый runtime-параметр в setup без необходимости. Значения 120 секунд — проектное решение этого плана, не характеристика установленного устройства.

## Этап 3 — сейчас: повторные попытки VPN и времени

- [ ] Инструментировать переходы `WG_WIFI → WG_TIME → WG_CONNECTING → WG_UP`, время в каждом этапе, коды SDK и число повторов. Не выводить endpoint/ключи.
- [ ] Проверить SNTP после Wi-Fi reconnect: сейчас старт выполняется при переходе online, а подключение WG запрещено при `time(NULL) < 1704067200`. Отличать ожидание времени от handshake; не обходить проверку времени.
- [ ] Изучить retry в используемом компоненте WireGuard прежде чем добавлять внешний reconnect. Тестировать bounded backoff и гарантировать отсутствие двух worker/netif; все raw lwIP операции оставить на tcpip_thread.
- [ ] Подготовить fake-тесты: NTP блокирован, DNS недоступен, новый DHCP-адрес, потеря Wi-Fi, AP setup, выключение VPN. Не менять ключи, маршруты или NTP-сервер вслепую.

## Этап 4 — сейчас: восстановление задачи

- [ ] При сохранённом request ID сначала показывать актуальный этап сети, затем «ВОССТАНАВЛИВАЮ» при lookup; «ДУМАЮ» использовать только для обработки на backend.
- [ ] Сохранить единственный ограниченный deadline восстановления (текущий 180 секунд), не перезапускать его на каждом retry или смене сетевого статуса. Сон после терминального исхода следует общей политике.
- [ ] Тесты: lookup 404, upload_failed, queued, ready, timeout, отмена; неизвестный исход не вызывает автоматическое создание новой записи. Терминальные ветки очищают ID согласно существующему контракту.
- [ ] Убедиться, что чтение состояния и HTTP выполняются вне UI/capture task. Запустить native-тесты, target build, commit/push каждого независимого изменения.
