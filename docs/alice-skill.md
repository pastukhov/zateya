# «Моя затея»: Алиса, KeenDNS и эксплуатация

Состояние на 28 сентября 2026: приватный навык опубликован владельцем,
связка Яндекс ID заработала, backend и proxy запущены на сервере.
В консоли Диалогов подтверждены авторизация и ответ на «проверка связи».
Сохранение настоящей идеи через Алису, дополнение через диктофон и разговор
с колонкой ещё требуют отдельной приёмки. Наличие зелёных тестов не заменяет её.

## Архитектура

```text
Алиса → HTTPS zateya.atitlan.keenetic.link:443
      → Keenetic → HTTP 192.168.11.2:7071
      → alice-proxy (Nginx в Compose)
      → backend:${VOICE_BIND_PORT}/api/alice/webhook
      → SQLite очередь → общий TextTurnProcessor → LLM → Obsidian → Git

Диктофон → сервер:7070 → аудиоконвейер → тот же TextTurnProcessor
```

На действующем сервере VOICE_BIND_PORT=7070; значение по умолчанию в Compose
— 8080. Proxy получает порт из той же переменной. Отдельного процесса backend
для Алисы нет. Распознавание и озвучивание в этом канале выполняет Яндекс;
модель LLM, контекст, Obsidian и Git общие с диктофоном.

Один экземпляр TextTurnProcessor сериализует обработку общего context_id.
Alice request_id имеет префикс `alice:`; источник содержит channel/client_id.
SQLite `data/archive/alice.sqlite3` хранит очередь, черновики, ответы на события,
подтверждение отмены и позицию чтения длинного ответа. Архивы задач находятся
в `data/archive/alice/<job-id>/`. OAuth-токены в очередь не записываются.

Повтор события `(skill_id, session_id, message_id)` проверяется по хешу и должен
возвращать сохранённый ответ. Worker возвращает прерванные running-задания в
очередь с прежними ID. На владельца допускается 8 queued-заданий и один
черновик до 12 000 символов. Бюджет webhook — 2 с вместе с авторизацией. При приёме новой записи
webhook коротко ждёт результат независимого фонового worker. Если обработка
успела завершиться, Алиса сразу озвучивает результат. Иначе отвечает
«Приняла запись, обработаю её в фоне.» без обязательной просьбы сказать
«Готово?». Ожидание не отменяет задачу. Первый ответ сохраняется в SQLite:
повторная доставка того же события возвращает тот же ответ даже после
завершения обработки. Команда «Готово?» остаётся доступна по желанию.
Подтверждение приёма в очередь не означает сохранение заметки в Obsidian.

## KeenDNS и proxy

В Keenetic создано веб-приложение `zateya.atitlan.keenetic.link`, направленное
на `192.168.11.2:7071`. HTTPS и сертификат обслуживает Keenetic. Веб-приложение
не должно требовать отдельного входа через браузерную форму Keenetic.

`deploy/alice.nginx.conf.template` разрешает только POST точного пути
`/api/alice/webhook`. Другие пути дают 404, другие методы этого пути — 405.
Лимит тела — 64 KiB, ingress rate — 10 запросов/с с burst 30; отдельная квота
backend — 30 запросов/мин на проверенного владельца. Клиентские заголовки
Forwarded/X-Forwarded-For/X-Real-IP не передаются как доказательство адреса.
Лог proxy содержит статус, метод и длительность, без тела, URL-параметров и токена.

Proxy использует обычную сеть Compose, не host networking. Постоянное состояние
ему не нужно; шаблон монтируется из deploy только для чтения. Остальные данные
остаются в папках data рядом с Compose.

## Яндекс ID и связка аккаунтов

1. Создать приложение **для авторизации пользователей**, платформа **Веб-сервисы**.
   Иконка проекта: `assets/branding/zateya-icon.png` (PNG меньше 1 МБ).
2. В Redirect URI указать `https://social.yandex.net/broker/redirect`.
3. Разрешить только `login:info` («Логин, имя и фамилия, пол»).
4. В навыке, во вкладке «Связка аккаунтов», сохранить:

| Поле | Значение |
|---|---|
| Идентификатор приложения | Client ID OAuth-приложения, не ID навыка |
| Секрет приложения | Client secret, не токен вида `y0_…` |
| URL авторизации | `https://oauth.yandex.ru/authorize` |
| URL получения токена | `https://oauth.yandex.ru/token` |
| URL обновления токена | `https://oauth.yandex.ru/token` |
| Идентификатор группы действий | `login:info` |

5. Сохранить тип доступа **Приватный** и опубликовать навык. В нашем запуске
   одной настройки черновика оказалось недостаточно: внутренний API каталога
   возвращал `404 Skill not found` для account_linking. После публикации
   авторизация заработала. Это наблюдение конкретного запуска, а не утверждение,
   что документация Яндекса запрещает тестирование авторизации в черновике.
6. В тестировании пройти авторизацию; убедиться в появлении «Вы авторизованы».

Webhook проверяет OAuth-токен из Authorization или session.user.access_token
через `https://login.yandex.ru/info` и сравнивает возвращённый id с
ALICE_ALLOWED_YANDEX_ID. Таймаут проверки — 1 с, положительный кеш — до 60 с.
Поля user_id/skill_id сами по себе не разрешают доступ. Без токена отдаётся
верхнеуровневый `start_account_linking` без response, если поверхность поддерживает
привязку; иначе текстовая инструкция. Платформенный ping не обращается к данным.
Событие завершения привязки обрабатывается отдельно от текста диктовки.

### Получить ID владельца без передачи токена в чат

Для ручной проверки добавить **второй** Redirect URI
`https://oauth.yandex.ru/verification_code`, сохранив адрес broker/redirect.
Получить ручной токен по инструкции Яндекс ID. Затем выполнить:

```bash
python3 - <<'PY'
import getpass, json, urllib.request
token = getpass.getpass('Вставь токен (ввод скрыт): ')
request = urllib.request.Request(
    'https://login.yandex.ru/info?format=json',
    headers={'Authorization': 'OAuth ' + token.strip()},
)
with urllib.request.urlopen(request, timeout=10) as response:
    print('ID владельца:', json.load(response)['id'])
PY
```

Токен вставляется в приглашение после запуска, не внутрь getpass в исходнике.
Если сохранять код в .py, строки `python3 - <<'PY'` и завершающая `PY` в файл
не входят. Токены, Client secret и cookies нельзя включать в Git или скриншоты
диагностики. Уже раскрытые токены/сессии следует отозвать или завершить.

## Конфигурация и обновление сервера

В `/opt/zateya/.env`:

```dotenv
VOICE_BIND_PORT=7070
COMPOSE_PROFILES=alice
ALICE_PROXY_PORT=7071
ALICE_ENABLED=true
ALICE_SKILL_ID=<ID навыка>
ALICE_ALLOWED_YANDEX_ID=<id из API Яндекс ID>
ALICE_CONTEXT_DEVICE_ID=<существующий ID диктофона>
```

Личные идентификаторы и секреты не нужны в публичном примере. Client secret
сохраняется в консоли Диалогов; backend получает пользовательский токен в запросе.
Значение ALICE_ENABLED по умолчанию в репозитории остаётся false.

```bash
cd /opt/zateya
git pull --no-rebase origin main
docker compose config --quiet
docker compose build backend
systemctl restart zateya
systemctl is-active zateya
journalctl -u zateya -f
```

Unit запускает Compose в foreground, поэтому stdout/stderr обоих контейнеров
попадают в journald. COMPOSE_PROFILES из .env включает proxy при запуске unit.
После изменения .env нужен recreate контейнера; один `docker compose restart`
не обновляет его окружение. Проверка диктофона: GET локального `/health/live` — 200.
Отключение канала: ALICE_ENABLED=false с пересозданием backend; при необходимости
также закрыть веб-приложение KeenDNS. Диктофон продолжает использовать свой порт.

## Команды и подтверждённое поведение

- «Проверка связи», «проверка, заметку не создавай», «проверка связи, заметку
  не создавай» вне открытого черновика: немедленный ответ «Связь есть, заметку
  не создавала», без LLM, задачи очереди и записи в Obsidian. Ответ завершает сессию.
- «Начни запись» → фразы → «Закончи запись»: сбор черновика и постановка задачи.
  «Продолжи запись» сохраняет уже набранное. Во время записи обычные вопросы,
  в том числе «Готово?», являются содержимым черновика.
- «Отмена» в открытом черновике требует подтверждения; состояние хранится
  на владельца в SQLite. Выход сохраняет черновик и принятые задания.
- «Запиши дословно: …» передаёт только остаток фразы.
- «Готово?» вне черновика возвращает состояние задачи или сохранённый ответ.
- «Дальше» возвращает следующую часть длинного ответа. Повтор одного webhook
  не перелистывает его ещё раз.

## Диагностика по результатам запуска

| Симптом | Что выяснили / действие |
|---|---|
| KeenDNS возвращает 502 | На сервере ещё не был запущен proxy на 7071 |
| POST webhook даёт JSON 404 | Работал старый backend без модуля Алисы; также проверить ALICE_ENABLED и обязательные параметры |
| Окно авторизации: «Произошла ошибка» | Network показал GET API каталога account_linking → 404 `Skill not found`; публикация приватного навыка решила проблему |
| Первый вход в тестирование: таймаут | Позднее исчез, причина не доказана. Локальная скорость backend не доказывает скорость пути от серверов Яндекса |
| Скрипт получения ID: 401 | В конкретном случае токен ошибочно вставлен в текст приглашения getpass, а не введён при запуске |
| ID выведен, затем NameError: PY | В .py попал разделитель shell heredoc; удалить завершающую строку PY |
| «Запись сохранила, но обновление заметок требует проверки» на тестовую фразу | LLM вернула create=false вместе с capture и wiki-правками. Writer отклонил публикацию, исходный текст сохранился. Добавлены точные служебные варианты проверки без обращения к LLM |

Последнее исправление не делает произвольную фразу «не создавай заметку»
детерминированной командой. Для иных запросов сохраняется LLM-контракт и
валидация writer; противоречивый результат по-прежнему может дать needs_review.
Предыдущее тестовое задание с таким статусом не удаляли и не переписывали.

## Проверки и что осталось

На версии `77bd0a3` прошли 455 backend-тестов, сборка на сервере, запуск unit,
локальный healthcheck 200 и проверка нового маршрута команды внутри контейнера.
Ранее отдельно прошёл `deploy/test_alice_proxy.py` с настоящими контейнерами
Nginx и тестового HTTP upstream: фильтрация путей/методов, передача JSON и
Authorization, лимит тела, отсутствие токена в логах.

Публичные пробы KeenDNS дали 200 на ping и запрос карточки привязки;
из локальной сети через публичное имя измерено 0,2–0,54 с. Это не измерение
из инфраструктуры Яндекса. Пользователь подтвердил публикацию и авторизацию;
на скриншоте зафиксирован успешный ответ на точную команду «проверка связи».

Осталось проверить отдельно:

- Реальную идею через Алису: заметка, wiki, Git commit/push.
- Alice capture → recorder amend и обратное направление, query/plan/build.
- Полный прогон на отдельном vault с bare origin: конфликт, повторы, рестарт.
- Колонку/телефон, длинную диктовку, паузы, кнопки и обновление OAuth-токена.
- Все пункты исходного плана: зелёные тесты не означают его полное выполнение.

Привязка проверяет аккаунт, а не голос человека возле колонки. Любой с доступом
к авторизованной поверхности может обращаться к навыку.
