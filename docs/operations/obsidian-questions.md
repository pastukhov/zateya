# Вопросы по заметкам Obsidian

Диктофону можно задавать обычные вопросы и продолжать разговор: «Какие варианты
отпуска на январь мы обсуждали?», «Почему выбрали Юннань?», «А какой из них
подходит для дайвинга?». Обязательных команд нет: модель различает вопрос,
уточнение, новую мысль и смену темы. Отвечает кратко, по-русски; служебные пути
и цитаты остаются в истории, а не читаются вслух. Режимы кнопки и автоматический
ответ на уточняющий вопрос не меняются. Обновление прошивки не требуется.

## Поиск и границы

Поиск читает Markdown во всём настроенном vault, включая ручные заметки вне
`Затея/`. Использует Unicode-нормализацию, упрощённое снятие русских окончаний,
названия, aliases и текст. Это локальный лексический поиск, без внешнего embedding
сервиса. Совпадения текущего вопроса важнее прежней темы; дополнительно включаются
не более четырёх соседних заметок по однозначным wiki-ссылкам. По длинным заметкам
передаются релевантные отрывки. Это подборка свидетельств, не разрешение на запись.

Стандартные пределы именно retrieval: 3000 Markdown-файлов, 512 КиБ на файл,
8 000 000 прочитанных байт, 20 000 записей обхода, проверка двухсекундного бюджета
между файлами/каталогами. Возвращается до 8 заметок с суммарно 16 000 символов
отрывков. Дополнительно — до четырёх коротких цитат на заметку, максимум 6000
символов цитат во всей подборке. Поиск пропускает скрытые пути, symlink,
attachments/assets, бинарные и не-UTF8 файлы. Файл, превышающий размерный предел,
не читается частично как полный источник. При изменении/удалении заметки новое
обращение читает актуальный текст; повтор того же запроса использует прежний
снимок для идемпотентности.

`search.coverage=bounded_local_scan` и `search.truncated` показывают границы.
Отсутствие совпадений не доказывает, что информации нет во всём vault.
Эти пределы не являются общим deadline всего запроса: прежний управляемый writer
контекст, Git, модель и TTS имеют собственные ограничения.

## Ответы и источники

Модель получает `retrieved_pages` отдельно от writable `pages`. Обычная заметка
из retrieval не становится целью writer. Даже инструкция внутри заметки —
недоверенные данные, а не команда менять файлы или раскрывать доступ.

Для ответа модель выбирает `answer.status`: `found`, `not_found`, `ambiguous`
или `conflicting`. Предпочтительный формат citation — `{ref: "q-…"}`: ID связывает
точную короткую цитату с конкретным путём и SHA256 снимка. Backend подставляет
исходное написание, название, каноническую Obsidian-ссылку и хеш. Совместимая форма
`{path, quote}` разрешена только при дословном совпадении в переданном отрывке.
Нельзя исправлять орфографию внутри цитаты или склеивать её через пропуск текста.

`found` требует хотя бы одну реальную цитату. `conflicting` требует две разные
цитаты; backend проверяет их происхождение, а смысловое противоречие оценивает
модель. Наличие цитаты само по себе не доказывает логическое следование ответа —
это остаётся границей модельного качества. Неизвестный ID/путь, выдуманная цитата
или некорректный query-контракт дают одну попытку исправления, общую с JSON repair.
Повторная ошибка даёт `unsupported` и честный безопасный ответ. `not_found`
озвучивает ограниченность просмотренных заметок, без придуманной цены или факта.
Речь/метаданные ответа ограничены одинаково 2000 символами.

Незавершённый разговор хранится по context/device и переживает рестарт backend.
Ссылки предыдущего вопроса заново читаются для короткого продолжения; прежняя
реплика ассистента не считается доказательством. Контекст уточнений и retrieval
истекает через 15 минут. Reset сессии очищает привязку продолжения, сохраняя архив;
новая опубликованная мысль завершает прежний retrieval-контекст.

## Вопросы не создают страницы

До удалённых вызовов исходная речь и её метаданные сохраняются в archive и DB.
Повтор с тем же request ID и другим текстом/метаданными отклоняется без перезаписи
оригинала. `query` сохраняет receipt в DB, но не создаёт Markdown: ни source,
ни idea, ни wiki, ни plan, ни index/log/schema. Сбой модели, TTS или Git не удаляет
сырой ввод и не превращает вопрос в опубликованную мысль.

При последующей настоящей операции записи текущий и явно использованный прежний
источники материализуются через общий crash journal. Исходные дата, request ID,
turn ID и channel сохраняются. Это позволяет сначала задать уточняющий вопрос,
потом создать мысль с корректной ссылкой на оригинальную диктовку. Старый API
`KnowledgeStore.capture` по умолчанию сохраняет прежнюю materialization-семантику
для внутренних callers; общий TextTurnProcessor использует deferred режим.

## История и API

После текстового результата рядом с transcript/reply/context/proposal хранится
`answer.json` с финальной произносимой репликой, статусом, цитатами и coverage.
При `needs_review` метаданные ответа не публикуются. При ошибке TTS текст/цитаты
остаются в архиве, но voice job не становится `ready`.

Все endpoints требуют `X-Device-Id` и bearer-токен этого устройства:

- `GET /api/voice/history` — до 20 последних ready jobs текущего устройства.
- `GET /api/voice/turns/{turn_id}/answer` — JSON ответа, максимум 64 КиБ.
- Прежние status/lookup включают только короткий `answer_url`, если ответ готов.
  Цитат внутри status нет: совместимость с буфером firmware 768 байт сохраняется.

Чужой, неизвестный или неготовый answer возвращает 404; без авторизации — 401.
История и ответ имеют `Cache-Control: private, no-store`. Старые ответы без
`answer_url` остаются допустимыми. Nginx разрешает только фиксированные маршруты.

## Приёмка

Проверяются ручные заметки, формы русских слов, aliases, длинные отрывки,
сравнение/короткий follow-up, смена темы, отсутствующие/противоречащие сведения,
инструкции внутри заметок, цитаты/неизвестные IDs, no-Markdown query, retry/restart,
целостность сырого ввода, reset, отдельный API и последующая запись новой мысли.
Реальный replay выполняется в отдельном временном vault. Успех серверных тестов
и модели не подтверждает физическое распознавание микрофона или воспроизведение
ответов на StickS3; это проверяется отдельно.
