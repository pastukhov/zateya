# Голосовые идеи в Obsidian: LLM Wiki и Ramble your idea, then build

Затея — голосовой вход в Obsidian vault. В Compose vault расположен в `data/obsidian/`; новые материалы пишутся в `Затея/`.

## Идеи, знания и планы

LLM Wiki сохраняет три связанных уровня:

- `sources/` — исходная расшифровка, которую writer не переписывает;
- `ideas/` — оформленная мысль с читаемым названием и стабильным `idea_id`;
- `wiki/` — связанные понятия, сущности и обобщения со ссылками на исходники.

`index.md` помогает навигации, `log.md` фиксирует изменения, а `builds/` хранит планы и задания. При дополнении агент получает релевантный контекст, а writer проверяет ссылки, источники и отсутствие конфликтующей ручной правки до записи.

Ramble your idea, then build — свободная диктовка, затем уточнение, запрос к базе, планирование и подготовка задания. Команда «реализуй» пока сохраняет задание в Obsidian: она не выбирает репозиторий, не запускает исполнителя и не меняет код.

Можно диктовать естественно: «дополни предыдущую мысль», «исправь бюджет», «что мы обсуждали про…», «составь план». Вопросы сами по себе не создают новые идеи. Если цель дополнения неоднозначна, Затея спросит уточнение.

## LLM API и границы доступа

Gateway обращается к `POST {LLM_BASE_URL}/chat/completions`. `LLM_BASE_URL` уже содержит префикс API: например `https://api.example/v1`, `https://openrouter.ai/api/v1` или локальный `http://localhost:11434/v1`. Автоматически добавляется только `/chat/completions`.

Обязательны `LLM_BASE_URL` и `LLM_MODEL`; `LLM_API_KEY` можно оставить пустым для сервера без авторизации. `LLM_RESPONSE_FORMAT` — `text` или `json_object`. Предел ответа LLM настраивается через `LLM_MAX_TOKENS`; единый deadline запросов — `LLM_TIMEOUT_SECONDS` (не больше 120 секунд). Если модель вернула неверный JSON или нарушила существующую схему, Gateway делает не более одной форматирующей попытки. HTTP-ошибки, отказ, обрезанный ответ и использование tools не запускают скрытый повтор или выбор другого провайдера.

В LLM отправляются транскрипт и ограниченный контекст. API-ключ не входит в prompt; модель не получает tools, доступ к файловой системе, Git или приватному SSH-ключу. URL и токены LLM/STT/TTS живут в серверном `.env` и не выдаются веб-интерфейсу устройства. Устройство знает только адрес Voice Gateway и собственный device token.

LLM, STT и TTS — отдельные сервисы и могут тарифицироваться отдельно. Gateway не выбирает модель вместо владельца и не делает fallback на другой API.

## Результат, повтор запроса и история

SQLite `/data/archive/llm-sessions.sqlite3` хранит локальные поколения диалога, проверенные LLM-результаты и короткую историю отдельно для каждого `device_id`. История содержит только транскрипт и окончательный короткий ответ; содержимое wiki-страниц в неё не копируется. Настройки `LLM_HISTORY_TURNS` и `LLM_HISTORY_MAX_CHARS` задают её предел.

Ключ идемпотентности — `(device_id, request_id)`. Повтор с тем же входом использует проверенный результат, с другим — возвращает `idempotency_conflict`. Результат LLM сохраняется до записи знаний, а историю Gateway фиксирует после успешной публикации или корректного запроса к базе и до синтеза речи. Поэтому ошибка TTS не вызывает повторную генерацию и не дублирует заметку.

Сброс сессии увеличивает поколение истории устройства, не удаляя Obsidian, архив или Git-историю. Пока у устройства идёт upload или voice job, сброс отвечает `409 device_busy`. Старая задача после reset не может пополнить новую историю.

Gateway сохраняет аудио, расшифровку, ответ и служебные результаты в `data/archive/YYYY/MM/DD/<turn-id>/`. Ограничьте права и срок хранения личных записей.

## Проверка и запись Obsidian

Исходный Markdown формирует backend на основании проверенной модели `HermesResponse` и `KnowledgeProposal`. Пути, идентификаторы, длины полей, источники и внутренние ссылки проверяются до записи. Несогласованность или ручная правка не перезаписываются молча: исходная запись остаётся доступной в `sources/`, а конфликт надо разобрать.

Голосовое подтверждение означает успешную запись в vault. Git push выполняется после этого в фоне.

## Commit и push в `origin`

Backend оставляет задание в `Затея/.sync/`. Единственный Git publisher внутри Gateway обрабатывает его периодически и использует `Затея/.sync/writer.lock`, общий с Obsidian writer. Он сверяет SHA-256 опубликованных файлов, делает selective commit и обычный `git push origin HEAD:<текущая ветка>`. Чужие staged-изменения сохраняются; force push, pull и rebase автоматически не выполняются. Несколько быстрых публикаций могут объединиться в один коммит.

После сбоя push задача остаётся в outbox и будет повторена без пустого коммита. Если файл изменили вручную после публикации, проверка хеша остановит синхронизацию и сохранит задание для разбора. Push не блокирует новые voice jobs.

Статус доступен через авторизованный `GET /api/voice/knowledge/git`; ответ содержит только статус, SHA commit и число обновлений. SSH private key и `known_hosts` находятся в `data/ssh`, смонтированном read-only. Процесс Git/SSH получает только нужное ему окружение; секреты LLM не передаются дочернему Git-процессу.

## Развертывание и данные

Рядом с `docker-compose.yml` сохраняются:

- `data/archive` — голосовой архив, база задач и новая история LLM;
- `data/obsidian` — существующий vault с его `.git`;
- `data/ssh` — ключ и `known_hosts` для публикации.

Используйте `deploy/prepare-data.sh`, чтобы привести владельца bind-каталогов к числовому UID/GID Compose. Скрипт не удаляет файлы, запрещает symlink внутри data и не создаёт пустые ключи. Существующие `data/codex` и `data/agent` во время перехода автоматически не удаляются и новым контейнером не используются.

Полный backup, настройка `.env`, перенос и откат описаны в [серверном runbook](../deploy/server-migration.ru.md).

## Происхождение подхода

- [Karpathy LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) — постоянная база знаний поверх исходников.
- [cerebro](https://github.com/andresbuonaiuto/cerebro) — организация источников, тематических страниц и противоречий.
- [llm-wiki ingest](https://github.com/ddsyasas/llm-wiki/blob/e8dd69ebba0dc7c395c1b8217bb1c30c14e8c84c/packages/core/src/ingest.ts) — разделение получения контекста, предложения и записи.
- [Rambler](https://github.com/BerkeleyHCI/rambler) — оформление смысловых частей речи.

Python-реализация и prompt адаптированы для Затеи; сторонний код в проект не копировался. Дополнительные Obsidian-плагины не нужны.
