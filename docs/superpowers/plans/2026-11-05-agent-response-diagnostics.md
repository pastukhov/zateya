# Диагностика повторяющегося agent_invalid_response

## Основание и границы

После исправления внутренней памяти диктофон подключается за 5,4 с и полностью
отправляет запись (HTTP202). Задания 11a8ae8c и 969b826f завершились на сервере
agent_invalid_response; initial требует invalid_json_contract repair, затем ошибка.
Архивный transcript/context совпадает с input_hash в sessions, история не менялась.
Несколько повторов отдельным процессом проходят схему, поэтому конкретное исправление
контракта или промпта пока не обосновано. OTA31 подписана локально, не опубликована;
аппаратная приёмка голоса остаётся открытой.

## Поведение

Добавить ограниченную безопасную диагностику ошибок JSON/schema в existing validator
и логировать её для initial и repair в OpenAICompatibleAgentClient. Не менять
допуск ответов, смысл, промпт, число модельных вызовов, fallback или публикацию заметок.
В диагностике только фиксированные имена полей схемы, индексы массива и типы ошибок.
Не выводить raw/input/msg/ctx, произвольные extra field names, transcript, ответы,
URLs, токены. Ограничить число ошибок и глубину пути; неизвестные элементы скрывать.
Существующие HermesValidationError.raw/detail оставить совместимыми для потребителей.

## Исполнение и проверки

1. Sol реализует минимальные изменения и regression tests: JSON syntax, schema
   initial+repair, extras с секретными именами, отсутствие личных значений в логах,
   прежнее успешное поведение и ровно одна попытка repair.
2. Основной агент независимо проверяет diff, запускает затронутые тесты и полный
   backend/deploy suite. Проверяет git diff --check, выполняет commit/push.
3. Серверный checkout 370319d отличается от main: сравнить только необходимые файлы,
   сохранить текущий image ID как rollback. Подготовить отдельный чистый checkout
   серверного commit с точным patch и добавить в существующий immutable image
   только два изменённых runtime-модуля. Это сохраняет все зависимости без их
   обновления при сборке. Не reset/pull и не менять .env.
4. Заменить только backend service с прежними config/mounts, проверить health и
   отсутствие новых ошибок. Сначала повтор архивного запроса без side effects;
   затем запросить одну физическую запись для точного диагноза.
5. По фактической ошибке отдельно уточнить план исправления. Не объявлять устройство
   исправленным и OTA установленной по результатам тестов/публикации.

## Проверка реализации

Основной агент проверил изменения независимо. Локальный полный suite: 869 passed,
13 failed исключительно из-за отсутствия ffmpeg на ноутбуке. В отдельном контейнере
из серверного образа с сетевым доступом, отключённым на время тестов, весь файл
MP3 generation и изменённые validator/client tests: 55 passed (включая все 13).
Новые регрессии проверяют синтаксис, схему, приватность и ровно одну repair-попытку.
Runtime-модули нового образа побайтово совпадают с проверенными исходниками.
Развёртывание и физическая проверка пока ожидаются.
