**Goal:** Устранить обрыв записи при задержках сети и определить пределы записи при нехватке пропускной способности.

**Architecture:** Измерить очередь захвата и TCP, затем исправить подтверждённое узкое место. Долговременное хранение записи — отдельное решение после расчёта памяти, не увеличение timeout вслепую.

**Tech Stack:** C, ESP-IDF 5.5.3, PlatformIO, Python/FastAPI, Docker Compose.

## Review Focus

Частичная запись сокета, длительный дефицит скорости, disconnect после отпускания,
потерянный ответ 202, повторный request ID. Проверить их в тестах и аппаратной матрице.

## Этап 1 — сейчас: воспроизведение на модели

- [ ] Описать наблюдение: около 21 КБ TCP за 2,06 секунды, FIN от клиента, сервер ACK без пауз. FIN не доказывает конкретную ветку ошибки прошивки.
- [ ] Host-модель: производитель 32000 байт/с, очередь загрузки 8192 и ring 32768, ограниченный потребитель. При 10000 байт/с дефицит 22000 байт/с; модель должна предсказать переполнение, а не «исправляться» таймаутом.
- [ ] Проверить нулевые/частичные записи, задержку открытия соединения, корректное завершение последнего HTTP chunk, odd PCM boundary и отмену без use-after-free.
- [ ] Подготовить отдельный Linux netns/контейнерный netem-стенд: RTT 20/300/600/1000 мс, jitter 0/100/300 мс, потери 0/1%, лимиты uplink 10/40/128 КБ/с. Программный клиент не заменяет измерения lwIP/ESP32.

- [ ] Зафиксировать решение с максимальной длительностью, носителем, восстановлением после питания, износом flash и поведением при исчерпании места. До согласования не менять кодек или API записи.
- [ ] Для первого исправления явно отделить «переживает временную задержку» от «сохраняет запись при постоянно медленном канале». Конечный буфер не решает бесконечный дефицит скорости.
